# UI 效果图 → 页面功能结构

把一张（或几张）页面视觉效果图，转成**开发能照着做出来的功能结构规格**。产出是一份 Markdown 文件：图上画了哪些区块、每个区块有什么字段、筛选怎么过滤、显示规则是什么、操作链路怎么走、状态怎么影响版式。

**内容来源只有两个**：① 图上可见的；② 用户明确书面说明的。每条都标来源。图上没有、用户也没说的，**一律进「待确认项」**——不猜、不编、不拿「同类页面一般怎么做」补。

**不产出**：API URL / 报文结构、数据库表与字段、前端组件代码、视觉与交互设计建议。这些各有归属，见文末边界表。

## 硬约束（最容易被静默违反，先记住再动手）

- **只提取图上有的**：正文只放两类内容——图上可见、用户明确说明（含你当场问出来的），每条标来源（`图 1` / `图 2` / `用户说明` / `用户确认`）。**图上没有的一律进「待确认项」**，推断只能出现在待确认的问法里（「是不是……？」），**不得写进正文当结论**；不许用「通常 / 一般 / 应该」糊过去
- **当场只问「卡住抽取」的问题**：图看不清认不出、这是哪一页、几张图是不是同一功能、图与文字矛盾到没法继续归并、缺关键图。**其余一律进待确认项留到最后统一问**——枚举取值全集、数据权限、校验规则、统计口径、状态流转、操作行为都不必当场问
- **待确认项收集完要逐项与用户确认，确认完才写最终文档**：不许带着一堆问号直接出稿。答了的进正文并标「用户确认」，用户明确说「先不确认」的才留进最终版的待确认项表
- **不许拿经验补**：不许拿「同类页面通常怎么做的」「后端一般怎么设计」「这类系统一般有」去填正文的空。这类知识只能变成待确认项里的一个问法
- **数据权限图上取不到，不许编**：效果图只画了某个用户看到的一屏，看不出数据是恰好归他还是所有人可见。用户说了就写并标「用户说明」；**没说就整节留空进待确认项**——不许从同类页面推断成结论，也不许默认所有人可见。这一节永远不许省
- **多张图属于同一功能时，合并成一份完整规格，不是一图一份**：先定图间关系（主页面 / 浮层 / 二级页 / 状态变体），再对齐字段与全局区块；图与图之间对不上（统计项、单位、按钮文案、状态名）**不许挑一张当准，也不许静默合并成一个**（怎么记见下一条）
- **图、文字、图与图之间矛盾时，两种口径都记下来进待确认项**，不静默择一；书面说明 > 图，但差异必须列出。**矛盾卡住抽取进行时才当场问**，否则留到最后统一确认
- **统计口径写到能对账**：统计对象、维度（数量 / 工时 / 金额）、时间范围、与列表筛选是否同源、单位（`个` / `人天`）。图上数字自相矛盾时（如各项之和 ≠ 总数）要指出来
- **筛选条件写到能实现**：一个条件作用于几个字段（多字段用 OR 连接）、与其它条件的关系（默认 AND）、值域与格式
- **显示规则落到字段级**：截断方式（`...` 不换行 / 换行 / 完全显示）、格式（`yyyy-MM-dd` / `2026.09`）、空值怎么显示
- **操作按链路提，不是按钮清单**：触发入口 → 打开的界面 → 输入项与校验 → 提交 → 反馈 → 数据与状态联动 → 可重复性，七段写全。静态图只画得出前两段，其余从多张图串出来（图 1 点击前 / 图 2 点击后），**串不出就标待确认**，不许猜「提交后会发生什么」
- **状态对版式的影响要写出来**：状态如何改变布局——追加标记、按钮增减、颜色、操作列内容
- **界面文案与业务字段名分开写**：图上的 label 是文案，字段名是它的**翻译性命名**（小驼峰、去掉单位后缀），必须能从文案直接推出；推不出就留空列待确认，**不许起一个图上没有的字段**。两者对不上时（`详情内容` vs `功能描述`）以业务字段名为准并注明界面文案
- **设计标注不是页面内容**：图上的虚线框、箭头、红字注释、尺寸标注是给开发看的说明，不要当成页面元素提取
- **不越界**：不写 API 契约、不写表结构、不写代码

## 工作流程

按顺序走，每步只读它链接的那一个文件；第 1–6 步共用一份规则，第 7–8 步用模板。**第 6 步是收口关卡，没过不许写最终文档。**

1. **定边界与图间关系** → [extraction-rules.md](references/extraction-rules.md#1-先定边界与图间关系)：这是哪一页（标题 / 所属模块 / 移动端还是 PC）、给了几张图、图与图什么关系（主页面 / 浮层 / 二级页 / 状态变体）、图里哪些是设计标注
2. **划功能区块** → [extraction-rules.md](references/extraction-rules.md#2-划功能区块)：从上到下切出查询区、筛选与统计区、内容区、操作区、弹层，确定各区块的层级与从属
3. **抠字段与显示规则** → [extraction-rules.md](references/extraction-rules.md#3-抠字段与显示规则)：每个区块的字段清单、界面文案、业务字段名、显示格式、截断与空值
4. **登记图上看不见的** → [extraction-rules.md](references/extraction-rules.md#4-图上看不见的登记不补)：数据权限、校验规则、统计口径、状态流转、空态 / 异常态、操作权限——**用户说过就写并标来源，没说过就登记进待确认项，不补**
5. **收集待确认项** → [extraction-rules.md](references/extraction-rules.md#5-图上看不出的信息标准问法)：逐条过「图上看不出的信息清单」，缺的写成待确认项并配上问法；**顺手审一遍正文，把混进去的猜测揪出来**
6. **逐项与用户确认** → [extraction-rules.md](references/extraction-rules.md#51-逐项与用户确认)：待确认项**收集完再统一问**，按「影响」排序、`AskUserQuestion` 分批（每批 3–4 项）；答了的写进正文标「用户确认」，用户跳过的留到第 9 节
7. **成文** → [spec-template.md](references/spec-template.md)：**确认完再落盘**，按模板输出最终 Markdown 到 `docs/feature-spec/<页面名>.md`（项目已有文档目录约定则跟随；用户指定路径则用用户的）
8. **自检** → 对照 [spec-template.md](references/spec-template.md#自检清单) 过一遍，特别是「正文里还有没有残留的待确认」

## 与其它 skill 的边界

| 这个 skill | 留给别的 skill |
|---|---|
| 图 → 功能结构（区块 / 字段 / 规则 / 权限 / 口径 / 待确认项） | 功能结构 → API 契约 → API 契约类 skill |
| 页面有哪些字段、字段怎么显示 | 资源的表与 CRUD 结构 → CRUD 代码生成类 skill；表字段命名 → `database-design-standards` |
| 图上看不出的信息该问什么 | 后端框架机制与异常错误码 → 后端框架类 skill |
| 页面功能结构本身 | 视觉风格、配色、组件选型、交互设计 → 不在本技能（不评美观、不给设计稿） |
